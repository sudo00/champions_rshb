# Передача backend и ML коллегам

## Текущее состояние

Связка FastAPI → MinIO/RabbitMQ → GPU-worker → PostgreSQL → HTTP-ответ реализована и проверена. Вызов `backend.worker.recognition.run(image: bytes, includeAlternatives: bool = True)` использует SAM 3, SigLIP2 и PaddleOCR GPU. Модели загружаются один раз на процесс. Численное ядро находится в `worker/pipeline`; переносить или менять его файлы без пересборки согласованного bundle нельзя: их SHA-256 проверяются при запуске.

В каталог включены 2 103 проверенные позиции. В контейнерном прогоне 76 магазинных фотографий сохранены Top-5, оценки, OCR и области базового v4 (порядок равнозначных текстовых свидетельств нормализован). Медиана полного HTTP-пути — 3,54 с, максимум — 4,69 с на RTX 3060 12 GiB. Это проверка паритета, не оценка точности на независимом наборе.

Внешние `/ready`, `/docs` и распознавание фотографии проверены. Адрес сервера передаётся команде отдельно и не фиксируется в Git. Внешний запрос с фотографией Массандры вернул ожидаемый slug примерно за 6 секунд.

## Точки входа и границы компонентов

```text
Телефон / Swagger / scripts/scan_api.py
  POST /v1/wines/scan
    backend/api/main.py::scan_label → submit_scan
      ├─ MinIO: байты фотографии
      ├─ PostgreSQL: задание со статусом pending
      └─ RabbitMQ: scanId, imageKey, includeAlternatives
           backend/worker/main.py::process_scan
             → load_image из MinIO
             → backend/worker/recognition.py::run(image, includeAlternatives)
             → worker/pipeline/wine_recognizer.py::WineRecognizer.predict
             → PostgreSQL: результат, status=done или failed
  GET /v1/wines/scan/{scanId}
    backend/api/scans.py::to_status_response
      → slug + Top-5 + карточки каталога + OCR + области
```

Контейнер API запускает `uvicorn api.main:app`; контейнер worker —
`python -m backend.worker.main`. Worker загружает модели один раз и слушает очередь.
API не импортирует модели. `recognition.py` — адаптер между контрактом backend и
ML-ядром; реализация поиска находится в `worker/pipeline/`. Старые неиспользуемые
заглушки `backend/worker/pipeline/{normalize,embed,search}.py` удалены.

## Как работать бэкендеру без видеокарты

### Локальные проверки контрактов

Из чистого Git checkout с установленным Docker:

```bash
make test-api
```

Команда собирает отдельный тестовый образ API и запускает его без сети.
GPU, веса, PostgreSQL, MinIO, RabbitMQ и работающий стек не нужны: внешние
зависимости заменены в тестах. Проверяются маршруты, ответы, readiness и обработка
ошибок; точность распознавания этими тестами не проверяется. Веса не скачиваются.
При проблемах сети сборки на текущем хосте: `make test-api TEST_BUILD_NETWORK=host`.

API-тесты сохранены в `backend/api/tests/`, тест адаптера — в
`backend/worker/tests/test_recognition.py`. Для последнего нужны зависимости
vision-окружения, но GPU не используется. ML-тесты в корневой `tests/` оставлены
локально и исключены из Git. Производственный образ API не содержит файлов тестов;
DEV-образ и отдельная цель `api-tests` содержат их.

### Настоящее распознавание на общем сервере

```bash
python3 scripts/scan_api.py photo.jpg --base <API_URL> --output result.json
```

Заменить `<API_URL>` адресом общего сервера, который передаётся отдельно.
Можно также открыть его `/docs`. На ноутбуке коллеги нужны только фото и Python;
все модели, очередь и база работают на GPU-сервере. Это проверка удалённого
развёртывания, а не изменённой локальной версии backend.

Для сквозной проверки изменений локального backend нужен отдельный тестовый
стек с GPU-worker либо согласованное развёртывание ветки на GPU-сервере.
Автоматического подключения локального API к удалённой модели сейчас нет:
worker связан с API общими RabbitMQ, MinIO и PostgreSQL. Без worker можно
разрабатывать API и каталог, но новые задания распознавания не завершатся,
а `/ready` не подтвердит готовность. Поддельного успешного ML-ответа в runtime нет.

## HTTP-контракт для приложения

### Отправка

`POST /v1/wines/scan`, JSON:

```json
{
  "imageBase64": "<base64 encoded image bytes>",
  "includeAlternatives": true
}
```

Успешный ответ содержит `success=true`, `scanId` (UUID) и `status=pending`. Некорректное изображение возвращает `success=false`; инфраструктурные ошибки могут возвращаться с HTTP 503. Проверять HTTP-код и тело ответа.

### Получение результата

`GET /v1/wines/scan/{scanId}` до `status=done` или `status=failed`. Между запросами можно выдерживать 0,5–1 секунду. Статусы `pending` и `processing` не являются результатами поиска. В ответе GET поле `success` не заменяет проверку `status`: при неудаче задания нужно обработать `failed` и `error`.

При `done`:

- `slug`: первый кандидат либо `unknown` при отсутствии целевого объекта;
- `wine`: полная карточка первого кандидата;
- `candidates`: до пяти объектов со `slug`, `rank`, оценками, свидетельствами и вложенной карточкой `wine`;
- `alternatives`: карточки остальных кандидатов, до четырёх;
- `observations`, `observedFields`: прочитанные надписи и извлечённые признаки фотографии;
- `regions`, `target`, `imageSize`, `coordinateSystem`: области и координаты;
- `message`, `warnings`, `cylinder`, `timingsSeconds`, `version`, `catalogSha256`: служебные данные обработки.

`includeAlternatives=false` возвращает одного кандидата. Внутренняя десятка поиска и первый результат от флага не меняются. `confidence=null`, `scoreIsProbability=false`: численные оценки не превращать в проценты уверенности. Полей F1 нет. Отсутствующие цены, рейтинги, годы возвращаются как `null`. `imageUrl` — относительный путь, его нужно разрешать относительно базового URL API.

Полный реальный ответ: [examples/scan-response.json](examples/scan-response.json). Схема: `/openapi.json`, [openapi.yaml](openapi.yaml). API принимает одиночные изображения до 30 MiB и 25 мегапикселей.

### Дополнительные ручки

| Ручка | Назначение |
| --- | --- |
| `GET /health` | Работает процесс API |
| `GET /ready` | Свежий heartbeat worker и совпадение версии каталога |
| `GET /v1/wines/search?q=...` | Поиск по настоящему каталогу |
| `GET /v1/wines/{slug}` | Карточка |
| `GET /v1/wines/{slug}/image` | Изображение карточки |
| `POST /v1/eval/predict` | Multipart `image`, синхронный плоский ответ `{"slug":"..."}` |

Оценочная ручка использует ту же очередь. По умолчанию ждёт до 9 секунд; исходный скрипт организаторов ограничивает запрос 10 секундами. На неё нельзя переносить контракт асинхронного мобильного API. Запускать оценку после `/ready`, последовательно, без конкурирующей GPU-нагрузки.

## Что уже хранится и где

| Ресурс | Текущее размещение |
| --- | --- |
| Каталог для API | `backend/catalog/catalog.jsonl`, читается API из файла |
| Копия карточек | Таблица `wines` в PostgreSQL, заполняется при старте API |
| Задания и результаты | PostgreSQL, таблица `scans` |
| Пользовательские фотографии | MinIO, bucket `storage` |
| Каталожные изображения | Файлы в bind mount API `/catalog-images` |
| Веса, индекс и снимок ML-каталога | Bundle, bind mount worker `/models:ro` |

Запись в таблицу `wines` сейчас не обновляет автоматически ни файловый каталог API, ни индекс модели. API использует файловый источник, а pgvector не участвует в текущем поиске.

## Что передать вместе с Git-репозиторием

1. Папку `weights/wine-recognizer-v4-memory-layout-release/` — примерно 8,09 GB. Внутри веса SAM 3 и SigLIP2, модели OCR, `features.npy`, `views.json`, `catalog.jsonl`, `manifest.json` и конфигурации моделей.
2. `data/deployment/catalog-images-v1.tar` и его `.manifest.json` — 2 103 изображения, около 152 MB. Распаковать в `data/deployment/catalog-images/`; внутри должна появиться папка `images/`.
3. При необходимости повторения оценки — отдельно `data/eval/` с исходным скриптом и примерами. Эти данные не входят в Git.

Веса не входят в Docker-образы и Git. Worker загружает локальные файлы; автоматического скачивания из HF или общего хранилища сейчас нет. Старый архив `weights/archive/wine-recognizer-v4-memory-handoff.tar` предназначен для передачи ML-компонента и не заменяет актуальную версию всего backend-репозитория.

## Развёртывание на новой машине: что работает сейчас

Проверенная платформа — Linux x86_64, RTX 3060 12 GiB, NVIDIA driver 580.178.04. Нужны Docker Compose v2, NVIDIA Container Toolkit и совместимый драйвер; Docker не устанавливает драйвер хоста. Для другой GPU/платформы провести отдельный smoke test. При сборке требуется интернет для образов, apt и Python-пакетов.

Ресурсы теперь разделены:

- `weights/wine-recognizer-v4-memory-layout-release/`: актуальный автономный bundle;
- `weights/research/`, `weights/source/`, `weights/cache/`: модели экспериментов, исходные веса и кэши;
- `weights/archive/`: прежние версии, не нужны для запуска текущего сервиса;
- `data/deployment/catalog-images/`: изображения каталога; исходные фото и отчёты тоже остаются в `data/`.

Bundle содержит также индекс и снимок каталога: это согласованный комплект
для инференса, проверяемый по SHA-256. Канонический каталог API остаётся в Git
в `backend/catalog/catalog.jsonl`. Изменение его карточек требует отдельного
обновления ML-индекса.

Для переноса подготовлен архив `weights/artifacts/wine-recognizer-v4-memory-layout.tar`
и файл `.tar.sha256`. Он содержит только ресурсы под `weights/`; код берётся из
этого Git checkout. Сборка архива: `python3 scripts/package_recognizer.py`;
существующий архив команда не перезаписывает. Размеры, SHA-256 и пути ресурсов записаны в [../build_env/artifacts.json](../build_env/artifacts.json).
Источник скачивания ещё не назначен,
загрузка в облако и автоматический downloader не выполнены.

При получении архива ресурсов проверить `.sha256` из доверенного источника,
затем распаковать архив из корня репозитория:

```bash
# Из каталога, где лежат полученные архив и его .sha256:
sha256sum -c wine-recognizer-v4-memory-layout.tar.sha256
# Затем из корня репозитория:
tar -xf /path/to/wine-recognizer-v4-memory-layout.tar
```

После копирования bundle и архива изображений:

```bash
mkdir -p data/deployment/catalog-images
tar -xf data/deployment/catalog-images-v1.tar -C data/deployment/catalog-images
make setup
curl -f http://127.0.0.1:8000/ready
```

`make setup` создаёт локальные env-файлы, собирает и запускает API, worker, PostgreSQL, MinIO и RabbitMQ. Это DEV-конфигурация. Команда ждёт `/health`, но не завершения загрузки моделей: дождаться успешного `/ready` отдельно.

Для PROD: `make env`, затем `make prod`; внешний порт задаётся `API_PORTS` в `build_env/.env.prod` (в шаблоне `80:8000`). Для заранее подготовленного окружения повторный запуск всего стека — одной командой.

На текущем компьютере из-за проблем bridge-сети используется дополнительный `docker-compose.host.yml` и проект `wine-integration`; его команда приведена в [API_RECOGNITION.md](API_RECOGNITION.md). Этот профиль и локальные VPN-правила не являются обязательной частью переноса на другой сервер. Не запускать второй проект поверх уже работающих контейнеров с фиксированными именами.

**На совершенно новой машине одного `docker compose up` пока недостаточно:** веса и индекс не скачиваются, а оборудование и доступ GPU должны быть настроены заранее. Воспроизводимый runtime проверен в контейнерах; полностью автоматический первичный запуск ещё предстоит реализовать.

## Что проверить бэкендеру при приёмке

1. `/ready` возвращает 200 после загрузки моделей; каталог содержит 2 103 карточки.
2. Отправить одно фото через `/v1/wines/scan`, дождаться `done`, проверить slug, карточку, Top-5 и загрузку `imageUrl`.
3. С `includeAlternatives=false` получить того же победителя и один элемент.
4. Проверить ошибку повреждённого файла и ответ `no_target` на изображение без объекта.
5. Запустить исходный `participant_test.sh` против `/v1/eval/predict`. Три успешных HTTP-запроса не означают три правильных совпадения: два примерных вина отсутствуют в каталоге.
6. Выполнить API-тесты (`make test` в обычном DEV-стеке), проверить обработку недоступных worker, очереди и хранилища на отдельном тестовом экземпляре.
7. На целевой машине повторить установку из чистого окружения с теми же версиями ресурсов. Не менять численный ML-пайплайн при интеграции.

Простой клиент: `python3 scripts/scan_api.py photo.jpg --base http://localhost:8000 --output result.json`.

## Оставшиеся задачи backend / deployment

### Для устойчивого общего прототипа

- HTTPS и контроль доступа, конфигурация секретов вместо демонстрационных значений Compose.
- Автоматическая доставка bundle и картинок с проверкой SHA-256 до запуска worker.
- Явное ожидание ML-readiness и понятная ошибка при отсутствующих ресурсах/GPU.
- Проверка восстановления заданий после рестарта worker, таймаутов/повторной доставки, ограничений очереди и хранения фотографий.
- Согласование мобильного контракта: polling, nullable-поля, реальные карточки, отсутствие mock-подстановки при ошибках.

### Для развития каталога

- Перенести каталожные изображения в S3/MinIO и выдавать их через API либо доступные клиенту URL.
- Перевести чтение карточек API на PostgreSQL; сохранить версионированный снимок для ML.
- Добавление/изменение карточки должно запускать подготовку эталонов и обновление индекса. Новую версию каталога активировать вместе с соответствующим индексом, с возможностью отката.

### Предлагаемый механизм автоматической поставки (ещё не реализован)

Хранить неизменяемые версии bundle и изображений в общем закрытом S3/хранилище артефактов. Указывать URL/версию и контрольные суммы в конфигурации релиза; доступ — через локальные секреты. Подготовительный шаг скачивает недостающие ресурсы во временную папку, проверяет SHA-256, атомарно публикует локальную версию и только затем запускает сервисы и ждёт `/ready`.

Для новой машины нужен заранее заполненный общий источник артефактов: пустой MinIO, который только что поднят тем же Compose, не может сам предоставить отсутствующие веса. При наличии ресурса в локальном кэше повторного скачивания не требуется.

## Граница ML-готовности

Бейзлайн поиска работает и сохранён при интеграции. Надёжный отказ для вина вне каталога и вероятности уверенности ещё не откалиброваны. Это ML-задачи; `no_target` решает отсутствие целевого объекта на фото, а не отсутствие конкретного вина в базе.

## Проверка уборки репозитория

Веса и фотографии не были включены в текущий Git-индекс. Добавлены исключения
`weights/` и корневой `tests/`; Docker-контекст также исключает веса, локальные
ML-тесты и env-файлы. Backend- и Android-тесты остаются в репозитории.
Каталог примерно 4,3 MB оставлен намеренно: он нужен API и согласован с индексом.
Исследовательские скрипты сохранены как исходники воспроизводимых экспериментов;
GPU-образ копирует из `scripts/` только два геометрических помощника.

Релиз `v4-memory-layout` сохраняет байты всех весов, индекса и каталога v4.
Единственное изменение среди хешируемых исходников — путь к OCR-кэшу в
экспериментальной функции `scripts/label_rectification_pilot.py`. Поэтому создан
новый manifest, а исходный v4 и его архив сохранены без изменений. Численный
алгоритм распознавания не менялся.

После переноса: 14 API-тестов прошли в автономном Docker без сети, 50 локальных
проверок адаптера и ML-ядра прошли. Два реальных запроса через очередь совпали
с сохранённым бейзлайном по Top-5, оценкам, OCR и областям; оценочная ручка
вернула ожидаемый slug Массандры. Это smoke test переноса, не новая оценка точности
или скорости. `/ready` подтверждает 2 103 карточки.

Текущие отслеживаемые файлы занимают примерно 5,62 MB. В объектах, достижимых
из всех локальных refs и reflog, нет файлов больше 10 MB. Служебная `.git`
занимает около 7 GiB: найдены три крупных локальных объекта, не достижимых
из refs/reflog, суммарно 3,90 GB до упаковки. Они не входят в обычный push/clone;
локальная очистка Git-объектов не выполнялась, история не переписывалась.
